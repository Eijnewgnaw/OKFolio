# 开源知识编译管线调研：从 Article 到可溯源 Concept 图谱

**调研日期：** 2026-07-20  
**范围：** 只使用项目官方文档、官方仓库源码和官方规范。比较目标是本项目的 `Article → ConceptRef → Cluster → Concept → provenance graph`，特别回答 429 个 Ref 不应一次性交给模型分区的问题。

## 结论先行

没有一个被调研项目采用“把全量候选一次性交给 LLM，要求每项唯一归入语义簇”的方式。可扩展项目都把 LLM 的上下文限定在**原子提取、有限候选判断或小簇摘要**，把全局一致性放在持久化的数据结构和确定性算法中。

对本项目最适用的组合是：

```text
Article（原文和锚点）
  → 每篇独立抽取多个 ConceptRef（LLM，结构化输出）
  → 代码召回跨文档候选边（词项 + 向量 + 类型约束）
  → 小批 LLM 边判定（same / related / separate）
  → 全局持久化 Ref 图，确定性受限并查集形成 Cluster
  → 对一个 Cluster 的成员证据做 map-reduce 联合编译 Concept
  → Concept → Ref → Article/原文锚点；related 边单独展示
```

这保留了跨批语义连贯性：**批次仅限制模型工作窗口，边和 Cluster 均是全局对象**。它也避开了本次 429 Ref、约 8 万字符、全覆盖 JSON Schema 请求造成的模型 `HTTP 500`。

## 对比总表

| 项目 | 原子单位与提取 | 全局合并/聚类 | 批次如何保持连续性 | 溯源与展示 | 与本项目的关系 |
|---|---|---|---|---|---|
| Google OKF reference agent | `Source.list_concepts()` 直接给稳定 `ConceptRef`；逐 Ref 读取、富化、写 Markdown | **不做**跨文档语义去重；源系统承担身份定义 | 一次只处理一个稳定 ID；已有 bundle 作为上下文 | Markdown 概念和链接；规范不规定 Ref/Cluster | 借鉴 bundle 边界，不可照搬其“Ref 就是 Concept”前提 |
| LangChain OpenWiki | 从代码库/连接器的本地原始资料合成 Markdown wiki | 以生成/更新 wiki 为主，不提供 Ref→跨源 Cluster 语义编译器 | SQLite checkpoint、增量 `--update`；来源实例独立 | OKF frontmatter + Markdown 链接；面向 wiki | 可借鉴 OKF 输出、更新与检查点，不能替代聚类器 |
| Microsoft GraphRAG | Document 切为 TextUnit；逐 TextUnit 提取实体、关系、可选 Claim | 同 `title + type` 的实体/同端点关系先确定性合并；再 Hierarchical Leiden 社区发现 | 抽取是局部的，合并后的全局图再聚类；社区报告按社区生成 | Document→TextUnit→实体/关系；Parquet 表；官方有可视化指南 | 最接近“全局图而非全量 prompt”的思想，但其实体同名合并规则对政策概念过粗 |
| LightRAG | 分块提取实体/关系；每条记录带 `source_id=chunk_key` | 同实体/关系累积 source IDs 和描述；超长描述用 map-reduce 摘要 | 并发与队列受限；合并状态写存储；摘要只吃一个实体/关系的描述列表 | 节点/边保留 source chunk ids，可据块生成引用 | 可直接借鉴「状态持久化 + 小对象 map-reduce + source ID」实现模式 |
| Cognee | `add + cognify + improve` 把资料转为持久图记忆 | 以图/向量存储为长期记忆层，支持本地 SQLite/Kuzu 和 Postgres 图后端 | 数据集和会话状态持久；而非一次性全量 prompt | 图+向量+元数据共同存储；官方产品强调检索/记忆，不是静态 wiki 生成器 | 借鉴运行态存储选择；不应引入整套运行平台来完成离线编译 |
| LlamaIndex PropertyGraphIndex | Document/Node 经可替换 KG extractor 生成路径/属性图 | 外部属性图库和向量检索；框架本身不定义跨文档 Concept 聚类语义 | ingestion pipeline 可异步和持久化，抽取器可替换 | Node metadata、docstore、property graph store 由应用建模 | 适合做组件库；不会替我们决定“何时两个政策概念相同” |

## 项目逐项证据与可借鉴点

### 1. Google OKF reference agent：稳定身份在上游，不做聚类

官方 `ConceptRef` 只有 `id`、`type`、`resource`、`hint`；`Source` 只要求列出并读取它们。也就是说 `list_concepts()` 返回的是**已被源系统确认身份的概念**，不是从自由文本临时抽出的候选。

- 源码：[ConceptRef 与 Source 接口](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/src/reference_agent/sources/base.py)
- runner 的 `enrich_all` 对 `list_concepts()` 的结果逐项处理：[runner.py](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/src/reference_agent/runner.py)
- 最终格式：[OKF v0.1 规范](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)

**对我们意味着什么：** OKF 是最终 `Concept` bundle 的交换格式，不是报告库的概念发现/聚类算法。我们的 `ConceptRef` 必须作为内部编译中间表示；它应含 `article_id`、原文锚点、逐字证据、候选类型、标题/摘要和提取版本。最终 OKF 中只发布 `Article`、`Concept` 及其 Markdown 链接，不把 Ref/Cluster 假装成最终知识。

### 2. OpenWiki：OKF wiki 和可恢复更新，不是跨文档语义合并器

OpenWiki 声明可以接入本地源或连接器，将它们合成为本地 wiki；其 README 明确声明输出 OKF v0.1 bundle，每个概念为带 frontmatter 的 Markdown，概念间 Markdown 链接表示关系。它还有 SQLite checkpoint 依赖、`--update` 和按 source instance 保留原始材料/清单的机制。

- 官方说明：[OpenWiki README：本地源合成与双模式](https://github.com/langchain-ai/openwiki#openwiki)
- [OKF 兼容条款及 Markdown links](https://github.com/langchain-ai/openwiki#open-knowledge-format-compatibility)
- [连接器原始数据、manifest、source instance](https://github.com/langchain-ai/openwiki#personal-knowledge-sources)

**差异：** 它解决“把资料维护成 agent wiki”，并未定义 `Article → 多 Ref → 跨 Article Cluster → 联合 Concept` 的可审计语义。它可指导我们的最终目录规范、增量检查点和 source manifest；不能替代全局 Ref 图。

### 3. Microsoft GraphRAG：局部抽取，全局图合并，再分层社区发现

GraphRAG 的数据模型显式区分 `Document`、`TextUnit`、`Entity`、`Relationship`、`Covariate`、`Community`、`Community Report`。Document 会保留到 TextUnit 的连接；TextUnit 是实体/关系的证据来源。默认 chunk 大小可配置，文档给出的默认值为 1200 tokens。

它的关键不是“将全图交给 LLM 分类”：每个 TextUnit 独立抽取子图；同 `title + type` 的实体合并并收集描述，关系按同源/目标合并；随后对已成形的图运行 Hierarchical Leiden，最后每个社区单独生成报告。

- [官方数据流与 provenance 说明](https://microsoft.github.io/graphrag/index/default_dataflow/)
- [官方索引架构、缓存和 workflow 可扩展点](https://github.com/microsoft/graphrag/blob/main/docs/index/architecture.md)
- [官方数据模型源码目录](https://github.com/microsoft/graphrag/tree/main/packages/graphrag/graphrag/data_model)

**可直接借鉴：** 将 `Ref` 视为本项目的 TextUnit 派生语义单元；持久化 `Article → Ref`；建立全局“已判定边”图后做图算法。**不可直接照搬：** `title + type` 适于实体同名归并，却会把“产业基金政策”“企业融资政策”等标题相近但约束、对象不同的决策概念误并。

### 4. LightRAG：把 LLM 只用于块提取和小对象摘要，合并状态全局持久化

LightRAG 的官方实现显示：

- 每个抽取实体/关系带 `source_id=chunk_key`；
- 合并节点/边时收集既有和新增的 source ids；
- 对同一实体/关系累积的描述，在超出上下文时采用递归 map-reduce：把描述拆成 token 可容纳的组，逐组总结，再对总结继续归约；
- 并发、队列和每个实体/关系保存的 source id 数量均可配置。

- [抽取和合并实现：`operate.py`](https://github.com/HKUDS/LightRAG/blob/main/lightrag/operate.py)
- [配置项与持久化 source id：`lightrag.py`](https://github.com/HKUDS/LightRAG/blob/main/lightrag/lightrag.py)
- [官方项目与离线部署文件](https://github.com/HKUDS/LightRAG)

**可直接借鉴：** 429 Ref 的大结果不能成为单次输出；每个 Ref、候选边批次和 Cluster 都要先落盘。联合编译 `Concept` 时采用 map-reduce：先按证据长度分组摘出不冲突的事实，再让 reduce 阶段写最终概念。每个 Concept 的 `source_ref_ids` 和每个 Ref 的 `article_id/anchor` 永不丢失。

### 5. Cognee：图、向量、元数据的长期运行态可共存，但目标不同

Cognee 官方定位是 agent 长期记忆：数据经 `add + cognify + improve` 进入自托管图；其 README 说明可在一个 Postgres 后端中共存图、文本、元数据与嵌入，也可在本地使用 SQLite、LanceDB、Kuzu。

- [官方 README：持久知识图、`add/cognify/improve`](https://github.com/topoteretes/cognee#quick-start)
- [官方 README：Postgres 及本地后端说明](https://github.com/topoteretes/cognee#one-stack-instead-of-four)
- [官方部署入口](https://github.com/topoteretes/cognee#docker-compose)

**判断：** 若未来需要在线增量摄取、多租户检索和 agent memory，Cognee 的存储组合值得评估；当前交付是离线 Docker 编译器 + 静态 site/graph，直接引入它会扩大部署面，不能减少“政策概念是否应合并”的业务判断。

### 6. LlamaIndex PropertyGraphIndex：可替换抽取器和图后端，不定义业务聚类

LlamaIndex 将连接器、文档节点、抽取器、属性图存储和检索器解耦；官方示例的 `PropertyGraphIndex.from_documents(..., kg_extractors=[...])` 体现了抽取器可以由应用替换，存储可以持久化或接入外部图库。

- [官方仓库：数据连接、结构化 index 与持久化](https://github.com/run-llama/llama_index)
- [PropertyGraphIndex 源码](https://github.com/run-llama/llama_index/tree/main/llama-index-core/llama_index/core/indices/property_graph)
- [KG extractor 源码](https://github.com/run-llama/llama_index/tree/main/llama-index-core/llama_index/core/indices/property_graph/transformations)

**判断：** 这是可选基础设施，不是完整方案。我们的 `ConceptRef` 和 `same/related/separate` 审计协议仍必须自定义。

## 推荐实现：429 Ref 的全局连续性和分批执行

### 数据合同（先于 prompt）

```text
Ref:        ref_id, article_id, anchor, evidence, kind, type, title, summary,
            entities/regions/times/policies, extractor_version
Candidate:  edge_id, left_ref_id, right_ref_id, retrieval_signals, status
Judgement:  edge_id, verdict(same|related|separate), rationale, model_run_id
Cluster:    cluster_id, ref_ids, canonical_signature, audit_status
Concept:    concept_id, cluster_id, article/ref provenance, body, links
```

`article_id + anchor + evidence_hash` 是不可变来源键。新一次运行只能新增 run/version，不能覆写旧证据再失去可复现性。

### 具体编排

1. **逐 Article 提取并验证。** 每篇产生多个 Ref，结构化输出在本地 schema 校验后立刻写 `refs.jsonl`；失败只重试该 Article/阶段。
2. **候选召回（代码，无 LLM）。** 先按 `kind/type`、同地域/主体/政策名、标题词、embedding Top-K 生成候选；排除同一 Article 的重复 Ref 以外的无关组合。候选是边，非分区。
3. **小批判边（LLM）。** 每个请求只放 20–50 条候选边以及每端的结构化摘要和短证据；返回 `same/related/separate` 和理由，不要求全覆盖。每批单独持久化、可重试、记录 tokens/耗时/模型版本。
4. **全局成簇（代码）。** 仅将通过硬约束的 `same` 边并入：`kind/type` 兼容、主体/地域/时间不矛盾、同一 Cluster 有可解释的 canonical signature。`related` 写为图边但绝不合并。
5. **链式误并审计（LLM，小簇）。** 对每个连通分量只审其成员摘要：若 `A≈B, B≈C` 但 A/C 主题不一致则拆边。这里的窗口是一个 Cluster，不是 429 Ref。
6. **联合编译（LLM，map-reduce）。** Cluster 成员证据过长时按来源分组先生成带 Ref ID 的事实卡，再 reduce 为一份 Concept；正文链接只连最终 Concept，侧栏/详情页呈现 Ref→Article→锚点。
7. **发布与验证。** 输出 OKF 的 Article/Concept Markdown、图的 nodes/edges JSON、`provenance.json` 和运行 manifest；验证每个 Concept 是否可回链到至少一个 Ref 和 Article，所有 `same/related` 边是否有 Judgment。

### 建议的首轮参数（可配置，不是硬编码）

| 参数 | 首轮值 | 目的 |
|---|---:|---|
| 候选 Top-K | 8 | 将 O(N²) 可能对缩为每 Ref 有限邻域 |
| 边判定 batch | 25 条 | 使 27B 模型的输入/结构化输出稳定可重试 |
| `same` 合并阈值 | 需 LLM `same` + 至少两项可解释召回信号 | 降低政策概念的同词误并 |
| Cluster 审计窗口 | ≤ 20 Ref/次；更大时按社区先分 | 防止再次出现大 JSON 请求 |
| Concept 联编证据 | 每次 ≤模型安全 token 预算；超出 map-reduce | 内容保真且不牺牲证据 |

## 对当前系统实验的决定

1. **保留** 56 篇已成功生成的 429 个 Ref；不要重跑发现阶段。
2. 将失败的“全量 `_cluster_refs()` 单模型调用”替换为上面的 `candidate_edges → judgement_batches → global_clusters → cluster_audit` 四个可恢复步骤。
3. `same` 边与 `related` 边分开：前者决定最终 Concept 成员，后者决定概念图谱边。这样图谱不会因强制合并而丢失“约束/比较/引用”等知识关系。
4. 静态站点至少提供两种入口：
   - **Article 页：** 保留全文，在首次相关处链接最终 Concept；
   - **Concept 页/图谱：** 展示概念关系，并展开 `Concept → Ref → Article → 原文锚点`。
5. 生产实验以“所有阶段产物可恢复、可溯源”为完成标准，不以“429 Ref 被一次性分完”为完成标准。

## 不建议采用的方案

- 不再把所有 Ref 及“每项恰好归属一个 Cluster”的约束放进单次 LLM JSON 输出。
- 不以标题相似或 embedding 阈值直接合并 Concept；它们只负责候选召回。
- 不把 Cluster/Ref 直接发布为 OKF 最终 Concept；否则会把中间不确定性暴露为知识事实。
- 不为了套用现成项目替换成整套 GraphRAG/LightRAG/Cognee：当前最小交付是已有编译器中的可审计 Ref 图和静态展示，外部框架只应提供可验证的设计借鉴。
