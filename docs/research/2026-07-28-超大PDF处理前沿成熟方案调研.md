# 超大 PDF 处理的前沿成熟方案调研

> 调研日期：2026-07-28  
> 目标：为《区域经济皮书》一类数百页、扫描/原生文本混合、包含图表的 PDF 设计离线、可恢复、可溯源的知识编译入口。

## 1. 结论

推荐采用“整本解析 + 统一文档中间层 + 结构感知分段 + 困难页回退 + 全链路溯源”，而不是先按固定页数把 PDF 切成若干篇文章，也不是把整本 Markdown 一次性送入通用大模型。

生产主路径建议：

1. 使用 **MinerU 3.x（优先当前稳定版）**整本解析 PDF。MinerU 3.0 起通过滑动窗口降低长文档峰值内存，并支持流式落盘；官方说明超长文档不再需要预先人工切分。
2. 不直接把 Markdown 当作唯一机器输入。将 MinerU 的 `content_list.json` / `middle.json` 规范化为项目自己的 `Document IR`，保留页码、坐标、阅读顺序、标题层级、表格和图片引用。
3. 一份 PDF 始终对应一篇 `Article`；在文章内部产生多个 `ArticleSegment`，再从 Segment 中发现 `ConceptRef`。
4. 分段采用 **Docling HybridChunker / Unstructured by-title** 所体现的成熟原则：标题与章节优先，只有超长语义单元才按 token 再切；同标题、同上下文的小块才允许合并。
5. 扫描、乱码、复杂表格或版面异常页，才路由到 MinerU VLM/Hybrid 或 PaddleOCR-VL；不能让所有页面都承担 VLM 的成本与不确定性。
6. 解析失败时按页段重试，但页段只是执行分片，不改变文章身份。合并时依靠稳定页码、块 ID、坐标和内容哈希去重。
7. LLM 不负责基础 OCR。LLM 用于标题树修复、跨页语义边界审核和异常复核，并以结构化输出和确定性验证器约束。

## 2. 为什么不应把“大 PDF”直接等同于“大模型上下文问题”

大 PDF 有三个不同问题：

| 层次 | 真正问题 | 成熟解法 |
|---|---|---|
| 物理解析 | 内存、渲染、OCR、失败重试 | 滑动窗口、流式落盘、页级任务、断点续跑 |
| 文档还原 | 阅读顺序、标题树、跨页表格、图文关系 | 结构化 Block、坐标、层级、跨页重建 |
| 语义编译 | 输入超出模型上下文、章节被切断 | 结构感知分段、局部上下文、分层汇总 |

即使服务端模型支持很长上下文，也不应把数百页原始 PDF 或整本 OCR 文本直接输入模型。上下文越长，成本、延迟、失败恢复难度和信息遗漏风险越高，而且模型无法替代可靠的页码和坐标溯源。

## 3. 主要开源方案比较

### 3.1 MinerU：最适合作为当前项目的生产主解析器

当前 MinerU 同时提供 pipeline、VLM 和 hybrid 路径，支持扫描文档、多栏、公式、表格、图片、阅读顺序、页眉页脚处理和跨页表格合并。3.0 起增加异步任务、Router、多 GPU 路由、长文档滑动窗口和流式写盘，工程成熟度与现有项目兼容性最高。

有价值的输出包括：

- `content_list.json`：按阅读顺序排列的扁平内容块，带 `page_idx`、`bbox` 和标题级别，适合稳定接入。
- `middle.json`：更完整的层次和中间结果，适合二次开发和问题排查。
- `content_list_v2.json`：按页分组、统一 `type + content`，但官方仍标注为 development version，核心数据模型不宜直接锁死在此格式上。
- `layout.pdf` / `span.pdf`：用于人工抽检和错误定位。

判断：**主选**。但应在其输出之上建立本项目稳定的 Document IR，隔离版本变化。

### 3.2 Docling：最值得借鉴的数据模型与语义分段设计

DoclingDocument 能统一表达正文、标题、表格、图片、章节树、阅读顺序、坐标和 provenance。其 HybridChunker 先按文档层级形成语义单元，再按 tokenizer 做细化：

- 仅拆分超过 token 上限的块；
- 仅合并标题、caption 等上下文一致的相邻小块；
- 表格跨 chunk 时可重复表头；
- chunk 携带原始文档元素和上下文元数据。

Docling Graph 的 provenance 进一步示范了 `document hash → chunk → page/bbox → character span` 的溯源结构。

判断：**不必立即替换 MinerU，但应作为 ArticleSegment 和 provenance 数据模型的主要参考**。

### 3.3 PaddleOCR-VL：困难页与扫描件的强回退解析器

PaddleOCR-VL 提供多页结果重建、跨页表格合并、多级标题恢复，并输出 block 标签、坐标和阅读顺序。其新版针对扫描、倾斜、弯折、复杂光照和不规则区域进行了增强。

判断：**作为困难页 challenger/fallback**。官方 benchmark 成绩只能说明通用测试集表现，不能直接等价为《区域经济皮书》上的实际效果。

### 3.4 Marker：优秀的结构化输出参考与备选解析器

Marker 可输出 Markdown、JSON、HTML 和 chunks。JSON 中有页面树、稳定块路径、polygon、children、`section_hierarchy`，metadata 中有目录、页统计和文本提取方式，也支持指定页范围。

其自带 API Server 官方明确定位为小规模使用，不适合直接作为大规模生产编排层。

判断：**适合抽样对照和中间层设计参考，不作为首选生产服务**。

### 3.5 Unstructured：成熟的分区与标题分段原则

Unstructured 的 `partition_pdf` 会根据文档特征在 fast、hi_res、ocr_only 等策略间选择；`chunk_by_title` 保留章节边界，并允许章节跨页。普通块不默认重叠，只有超长块发生文本切分时才使用 overlap，避免重复内容污染。

判断：**适合借鉴路由和 chunking 规则**。其官方也提示 `hi_res` 在不可提取文本的多栏文档上可能出现阅读顺序问题，因此不能把自动策略视为无需验证。

### 3.6 olmOCR：成熟的批处理、重试和对象存储编排参考

olmOCR 将 PDF 按 page group 形成工作项，提供页级最大重试次数、最大错误率、并发 worker、远程推理和 S3 workspace。

判断：**适合借鉴任务队列和失败恢复模式**，不作为中文政务/皮书解析质量的第一选择。

## 4. 推荐的数据结构

```text
Article（一本 PDF）
├── SourceDocument
│   ├── file_hash / page_count / parser_version
│   └── original_object_uri（私有对象存储）
├── Block[]（解析器输出的最小可溯源单元）
│   ├── block_id / type / text
│   ├── page_idx / bbox / reading_order
│   ├── heading_path
│   ├── asset_ref
│   └── content_hash
├── ArticleSegment[]（结构感知的模型输入单元）
│   ├── segment_id / heading_path
│   ├── block_ids[] / page_range
│   ├── text / token_count
│   └── prev_context / next_context
└── ConceptRef[]
    ├── ref_id / assertion
    ├── evidence_block_ids[]
    └── source_span
```

关键原则：

- `ArticleSegment` 是计算单元，不是新文章。
- `ConceptRef` 必须引用 Block，而不是只引用一段被模型改写后的文本。
- 图片上传 MinIO 后，Block 只保存对象 URI、hash、caption 和来源页，不把图片二进制塞进模型输入。
- 下游 Concept 由多个 Article 的 ConceptRef 聚类和联合编译，仍可一路回溯到 PDF 页码和区域坐标。

## 5. 不破坏语义的分段算法

### 5.1 一级边界：文档结构

优先级依次为：

1. PDF 书签/目录与解析器标题级别；
2. 标题编号模式（章、节、一、（一）、1.1 等）；
3. 版面特征（字号、粗体、居中、标题块）；
4. LLM 对候选边界的局部审核。

页面边界不等于语义边界。一个章节可以自然跨多页。

### 5.2 二级边界：token 上限

仅当一个结构段仍过长时，按段落、列表、表格等完整 Block 继续切分。建议初始实验使用：

- 目标：8k–12k tokens；
- 硬上限：16k–24k tokens；
- 上下文：携带 `heading_path`、上一段尾部摘要或少量原文、下一段标题；
- 不对所有正常段做固定 overlap。

具体阈值必须结合内网模型真实 `max_model_len`、吞吐和输出上限再定。

### 5.3 表格与图片

- 表格独立成块；跨页时先由解析器合并，若必须拆分则每块重复表头。
- 图片与 caption、正文引用、来源页绑定。
- 图像上传对象存储后生成稳定 `asset_id`，LLM 输入使用短期可访问 URI 或按需取回，不暴露长期凭据。

## 6. 失败回退与断点续跑

整本解析是逻辑主路径，但执行层必须支持页段级恢复：

1. 整本提交 MinerU；
2. 若任务 OOM、超时或输出页数不完整，定位失败页范围；
3. 仅对失败范围建立 page shard，可带前后 1–2 页作为上下文；
4. shard 中只有 core pages 获得最终所有权，overlap 页仅供上下文；
5. 按 `document_hash + page_idx + bbox + content_hash` 确定性合并；
6. 单页仍失败时切换 MinerU VLM/Hybrid 或 PaddleOCR-VL；
7. 超过重试阈值进入人工复核队列，不悄悄丢页。

不要只依赖 MinerU 服务进程内的任务状态。项目自身应持久化 job、attempt、parser version、输入/输出 hash 和每页状态，进程重启后可恢复。

## 7. 质量控制

解析质量不应只看“Markdown 看起来完整”。建议至少记录：

| 指标 | 含义 |
|---|---|
| page coverage | 输出覆盖页数 / PDF 总页数 |
| block coverage | 有效内容块比例、空页和异常页 |
| reading-order error | 多栏与图表附近阅读顺序错误 |
| heading-tree accuracy | 标题层级与章节归属准确率 |
| boundary continuity | 分段处是否截断句子、表格或论证链 |
| table integrity | 跨页表格、表头、单元格结构是否完整 |
| asset linkage | 图片、caption、正文引用是否正确关联 |
| provenance coverage | ConceptRef 可回溯到页码和 Block 的比例 |
| parser disagreement | 主解析器与 challenger 的结构差异 |
| cost/throughput | 页/秒、GPU 时、重试率、峰值显存 |

模型产生的 ConceptRef 还应通过确定性验证：

- 引用的 Block 必须存在；
- evidence 文本必须能在 Block 中定位；
- 页范围必须连续且合法；
- 不允许模型虚构图片、表格或来源；
- 结构化 schema 校验失败则重试或进入审计，不直接发布。

## 8. 面向当前数据的实验建议

先选三本代表性 PDF 做冻结样本：

1. 全扫描大文件：验证 OCR、长文档资源占用和失败恢复；
2. 原生文本/图片混合：验证读取顺序、图文关联和表格；
3. 字体或编码异常：验证自动 OCR 路由和乱码识别。

每本抽取固定页段作为人工金标，覆盖目录、普通正文、多栏、跨页表格、图表、章节交界。比较：

- MinerU pipeline；
- MinerU hybrid/VLM；
- PaddleOCR-VL 困难页回退。

实验先确定“页面/Block/标题树是否可靠”，再运行 ConceptRef 与 Concept 编译。否则下游模型会把解析错误包装成看似完整的知识资产。

## 9. 对当前项目的最终建议

本项目无需更换知识编译主架构，也不应让 OpenWiki/OKF 直接负责 PDF 切分。新增一个明确的“文档摄取层”：

```text
PDF
  → Parser Router
  → MinerU / fallback parser
  → Document IR
  → Structure-aware ArticleSegment
  → ConceptRef discovery
  → cross-document Concept compile
  → Bundle / Graph
```

这条路线兼顾：

- **前沿能力**：VLM 文档解析、跨页重建、长文档滑动窗口；
- **成熟工程**：结构化中间层、持久化任务、页级重试、断点续跑；
- **知识质量**：结构优先分段、证据级溯源、确定性验证；
- **保密部署**：解析、模型、MinIO 均可在内网离线运行。
