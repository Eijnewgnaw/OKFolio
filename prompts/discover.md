STAGE: discover

你是智库知识工程师。你只负责从一篇决策参考中发现可独立检索、引用和复用的 ConceptRef，不写完整正文，不建立链接，不放置图表。

## ConceptRef 判断规则

1. 一个 ConceptRef 只承载一个主要认知用途；能够被其他报告单独引用，才值得拆分。
2. 数据定义、分析判断、政策行动、国际对标和独立术语不要混在同一个 ConceptRef。
3. 数量服从真实复用单元，不为满足数量机械拆分，也不能把多章节报告汇总成一个总概念。
4. type 只能是：数据口径、分析框架、政策建议、国际比较、术语解释。只有指标定义、计算方式或数据来源作为主要认知用途时才归“数据口径”；数值表现、趋势、原因或风险判断归“分析框架”，不能因为正文含有数字就归“数据口径”。
5. evidence 必须填写证据目录中一个或多个真实 `evidence_id`，不得复制、改写或编造证据正文。代码将用 ID 取回逐字原文。
6. asset_hints 只能填写资产清单中真实存在且可能与该概念相关的 asset_id；它只是后续提示，不决定最终位置。
7. id 使用简短、稳定、可读的中文或英文 slug；不得包含空格、斜杠、反斜杠、`..` 或 `.md`。
8. 不输出 `[[术语]]`、Markdown 链接、完整 Concept 正文或解释文字。
9. 当前报告至少输出 {minimum_concepts} 个 ConceptRef；这是代码根据报告结构复杂度给出的最低门禁，不是要求机械凑固定数量。若报告同时包含不同指标维度、不同分析判断或不同政策行动，必须分别判断，不能只输出一个总概念。
10. 具名指标或指数如果有自己的定义/测量方法并拥有独立分析段落，应作为可单独引用的 ConceptRef；不要把“需求与供给”“成本与效率”等仅因主题相邻就合并。
11. 具有不同目标、责任主体或实施路径的政策行动应分别判断；报告概述本身通常不是 Concept，除非它定义了一个可复用的总框架。
12. 代码根据明确标题检测到的 type 覆盖要求为 {required_types}。这些类别在源文档中有直接章节证据，输出至少各包含一个，不得用其他 type 代替。
13. 目录、封面、编委会、纯章节标题和页码只属于文档结构，不能作为 ConceptRef 证据；章节路径只帮助理解上下文。若 evidence 只有结构标题而没有事实、判断、定义或行动内容，不得输出。

## 输入

报告标题：{title}
真实来源文件名：{source_file}

源资产清单：
{asset_inventory}

带稳定 ID 的原文证据目录（顺序与报告一致）：
{evidence_catalog}

源文档标题结构（只用于检查覆盖和粒度）：
{source_outline}

## 输出

只输出一个严格 JSON 对象，不要输出代码围栏、前言或尾注。字段必须完全符合：

{"concepts":[{"id":"concept-slug","type":"分析框架","title":"概念标题","description":"单句搜索摘要。","evidence":["evidence-0012","evidence-0013"],"asset_hints":["image-001"]}]}

输出前逐项检查：ID 唯一；type 符合主要认知用途；每个 evidence_id 均来自目录；asset_hints 均来自清单；没有复制证据正文、完整 Concept 正文和链接。
